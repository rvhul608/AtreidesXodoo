# UI brief: frontend teammate

You are building the **frontend** for a hackathon project (Odoo x Make-A-Ton 9.0, virtual round): a **Subscription Management System** for a fictional company, Brightloop Software. Backend agents (Claude Code, Codex, Lead Codex) are building the API at the same time. You own the `frontend/` folder. Judges look at the UI, UX, frontend quality and live behaviour, so this matters a lot.

If this brief conflicts with the existing repo layout, the repo wins; tell the human.

## How you work with the backend

- The source of truth is **`docs/api-contract.md`** (the Lead Codex writes it). Read it before building. Don't invent endpoints.
- Until an endpoint exists, build against **mock data that matches the contract exactly** (a mock layer such as MSW, or a small fake API module). Switch each screen to the real API as modules merge into `main`. Put every API call in **one API client module** so switching mocks off is a one-line change per endpoint.
- If a contract shape blocks you or looks wrong, tell the human and the Lead Codex. Do not edit backend folders.

## Stack (confirm with the repo)

React + Vite + TypeScript. A small component library or plain CSS/Tailwind is fine; **no external services** (fonts self-hosted or system fonts, no CDN-only assets that break offline). Real-time updates via **Server-Sent Events** (`EventSource`) from the backend.

## Hard rules

1. **Real data only.** Every list and dashboard comes from the API, never hard-coded JSON. Mock data is a development aid only and must be switched off before the end.
2. **Live updates must be visible.** Dashboard counters, invoice list and the Ops Monitor update without a page refresh when the backend emits events. Handle disconnects and reconnects gracefully.
3. **Performance.** Paginate and filter server-side. Show loading skeletons, keep pages responsive with 10,000+ rows in the database.
4. **Security in the client.** Never store tokens in localStorage (auth is an httpOnly cookie). Hide actions the role cannot use, but remember the backend enforces permissions. Customers must only ever see their own data.
5. **Don't show unfinished features.** Remove dead buttons and placeholder screens. Never claim what doesn't work.

## Git rules (strict)

- Your own branch (`ui/<topic>`, e.g. `ui/design-system`, `ui/dashboard`), your **own GitHub identity**. Verify `git config user.name` and `user.email` match your GitHub account before your first commit. Never `--author`, never global config, never commit for someone else.
- Small commits after each finished piece. Format: `type(scope): imperative summary` (15 to 72 chars), types `feat fix refactor test docs perf chore ui`. Add a 1 to 3 line body for anything non-obvious. Banned messages: "update", "fix", "wip", "changes", "misc", "final". Example: `ui(invoices): add explain-amount drawer with rule trace`.
- `git pull --rebase origin main` before pushing; make sure the app builds.
- **Merge to `main` at least once per hour** via pull request; the Lead Codex reviews. Use **"Rebase and merge"** so authorship is kept.
- Never force-push, never rewrite pushed history, never `--no-verify`.
- You will be asked about your commits. Write `docs/walkthroughs/frontend.md`: structure, state management, how live updates work, design decisions.

## Roles and portals

Three experiences from one login: **admin** (everything, including staff creation and discount rules), **staff** (day-to-day: customers, subscriptions, invoices, payments, no admin-only settings), **customer** (portal: only their own subscriptions and invoices, plus actions the plan allows such as pause, renew or close). Route guards by role.

## Screens to build

**Phase 1: core (functional first, simple but clean)**
1. **Auth:** signup (live password rule checklist: more than 8 characters, uppercase, lowercase, special character), login, forgot/reset password. Show clear validation and server errors.
2. **Layout:** sidebar by role, top bar with user menu, notification area for live events, consistent page header and breadcrumbs.
3. **Catalog (admin/staff):** products table + form with variants (e.g. brand "Odoo" adds 560), taxes.
4. **Plans and templates:** plan form (period, min quantity, availability dates, flags: auto-close, early close, pause, renew); quotation template builder (plan + lines, validity days).
5. **Subscriptions:** list with status chips and filters, create from template, detail page with lines, status timeline (Draft, Quotation, Confirmed, Active, Closed) and only the transitions the plan allows.
6. **Invoices:** list with status chips (Draft, Confirmed, Paid, Overdue badge), detail with lines, taxes, discounts, totals; actions confirm, cancel, send, **print view** (clean print stylesheet).
7. **Payments:** record payment dialog (method, amount, date, note), payments per invoice, outstanding balance.
8. **Finance dashboard:** active subscriptions, revenue, amount owed, overdue invoices, payments; filters (date range, customer, status), summary cards, charts, live-updating.
9. **Customer portal:** my subscriptions, my invoices, allowed actions.
10. **Admin:** staff management, discount rules (fixed/percent, minimums, dates, usage limit, scope), outbox viewer (sent reset links and invoices).

**Phase 2: extras (add each screen only once its backend exists)**
- **Explain this amount:** drawer or page on an invoice line showing each rule, whether it was applied or skipped, why, and the numbers.
- **Billing Time Machine:** pick a future date, run the simulation, show projected invoices, renewals, expirations, discounts and overdue balances, clearly labelled **simulation, no data changed**.
- **Revenue Leakage dashboard:** missed billings, duplicates, wrong discounts, unreconciled payments, estimated amount at risk, CSV bank statement upload with match review, one-click recovery actions with confirmations.
- **Billing Ops Monitor:** live billing runs, throughput, failures and retries, run preview (what would be created or skipped and why).
- **Renewal queue** and **overdue chase list** with reminder stages.
- **MRR/ARR** view with trend chart and next-30-days forecast.

**Phase 3: best UI/UX**
Shared design system (colour tokens, typography, spacing, buttons, inputs, tables, chips, dialogs, toasts); empty, loading and error states everywhere; responsive layouts; keyboard and accessibility basics (labels, focus states, contrast); light/dark optional; consistent number, currency and date formatting; sensible defaults and fewer clicks on the demo path. Prioritize the finance dashboard, invoice explain view, Time Machine, leakage dashboard, live Ops Monitor and the customer portal, because they carry the demo.

## Definition of done

Each screen: matches the contract, works for each role it is meant for, handles loading, empty and error states, has no hard-coded data, and is merged to `main`. At the end, run the full demo flow against the real backend from a clean clone.

## Demo flow to keep working

1. Sign up and log in as admin, staff and customer. 2. Admin creates a product with the Odoo variant (+560), a plan and a discount. 3. Staff creates a subscription from a template and activates it. 4. Run billing; invoice shows tax and discount; open "Explain this amount"; run billing again with zero duplicates. 5. Record a payment; the invoice flips to Paid and the dashboard updates live. 6. Leakage dashboard and the Time Machine. 7. Dashboard filters fast on 10,000 subscriptions; live Ops Monitor. 8. Customer portal shows only that customer's data.
